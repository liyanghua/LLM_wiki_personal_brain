# 一、项目背景与产品定位

## 1.1 项目背景

这个仓库最初的核心定位是一个 **Personal Brain OS**，即一个以个人知识沉淀、wiki 编译、结构化资产生成、Agent runtime 为核心的本地化知识系统。它不是一个通用聊天机器人，也不是一个纯文档检索器，而是一个“原始资料 -> wiki -> 结构化资产 -> agent/runtime/skills”逐层编译的系统。

从仓库的 `AGENTS.md` 到现有代码结构，都强调了以下四层边界：

1. `raw/`：原始来源层
2. `wiki/`：人类可读的知识编译层
3. `ontology/` 与 `memory/`：结构化资产层
4. `agent/` 与 `skills/`：交互运行与复用层

这个分层实际上非常重要，因为它保证了系统不会退化成“一个把所有东西都塞进 prompt 的聊天框”，而是保留了长期知识演化能力。

## 1.2 产品蓝图定位

根据两个 PRD 文档：

- [docs/prd_all_v1.md](/Users/yichen/Desktop/OntologyBrain/LLM-wiki/docs/prd_all_v1.md)
- [docs/prd_interaction_QA.md](/Users/yichen/Desktop/OntologyBrain/LLM-wiki/docs/prd_interaction_QA.md)

项目正在从 `Personal Brain OS` 向一个更高层的产品演化，即：

**Expert Brain Studio：行业专家知识榨取与知识生产工作台**

这个产品不是通用知识库，也不是问答助手，而是一条“专家知识生产线”。蓝图中的整体产品方向是：

- 交互式问答 Agent
- 共编 Copilot Agent
- 标注 Agent
- 冲突裁决 Agent Council
- Skill Creator + 自进化
- Governance Center

也就是说，最终目标不是“回答一次问题”，而是把专家知识从聊天和文档中榨取出来，逐步沉淀成：

- 可编辑的知识页
- 可治理的候选资产
- 可结构化的 ontology / memory
- 可复用的 skill
- 可被后续模块消费的标准对象

## 1.3 当前阶段定位

当前阶段并不是直接做完整的 Expert Brain Studio，而是聚焦蓝图中的第一个模块：

**交互式问答台 / Interactive Interview Console**

这一阶段的产品目标不是“聊得自然”，而是：

- 围绕一个主题做多轮递进式追问
- 榨取概念、规则、案例、信号、边界
- 让专家看到系统正在提炼出的候选知识
- 将 session 结果转成可供后续共编/标注/治理消费的标准对象

这也是本轮实现的核心方向。

# 二、当前阶段的产品目标与问题定义

## 2.1 当前阶段要解决的问题

`prd_interaction_QA.md` 明确指出，传统访谈和问卷的问题在于：

- 抽取深度不足，只拿到表层经验
- 结构化差，最后停留在纪要层
- 追问质量不稳定，容易漏掉关键变量、边界和反例
- 专家体验差，无法持续高质量配合

因此，这一阶段系统要解决的不是“做一个更智能的问答框”，而是：

**把行业专家脑中的 tacit knowledge 高质量榨取出来，并沉淀成可进入后续知识生产链路的候选资产。**

## 2.2 本阶段的核心 MVP 目标

这一阶段的 PRD 目标可归纳为七个子模块：

1. Session 创建
2. 递进式问答引擎
3. 候选知识实时抽取
4. 待追问问题池
5. Session 收束与总结
6. 专家修正与确认
7. 输出到后续模块

在这七项中，本轮实现真正重点补齐的是 1、3、4、5、6、7 的产品对象层，而不是重复建设 2 的基础引擎。

因为 2 递进式问答引擎在此前版本里其实已经有较多基础：

- `ProblemCompiler`
- `QuestionPlanBuilder`
- `RetrievalPlanner`
- `StoppingCriteria`
- `WritebackStager`
- `AgentTrace`

真正缺的是：**它生成了过程，但还没有生成 PRD 所要求的“产品产物对象”。**

# 三、升级前的系统现状

## 3.1 升级前已有能力

在本次升级前，系统已经具备一条较完整的问答与 extraction 基础链路：

### 后端已有能力

在 [src/personal_brain/extraction/service.py](/Users/yichen/Desktop/OntologyBrain/LLM-wiki/src/personal_brain/extraction/service.py) 中，`ExtractionInterviewService` 已经具备：

- 启动 interview
- 获取历史 state
- 继续多轮追问
- finish 收束
- state 持久化
- current trace / per-turn trace
- staged writeback

核心流程如下：

1. 问题进入
2. `ProblemCompiler` 做问题编译
3. `RetrievalPlanner` 做四桶检索
4. `AnswerPlanner / AnswerComposer / StyleEngine` 生成当前回答
5. `QuestionPlanBuilder` 生成下一问
6. `StoppingCriteria` 判断是否停止
7. `WritebackStager` 生成 staged writeback
8. `StateTracker` 持久化状态

### 检索层已有能力

系统已经不再是最初的简单关键词检索，而是叠加了：

- wiki-first retrieval
- raw evidence-only augmentation
- qmd 风格 search provider 抽象
- retrieval buckets
- retrieval explain
- 可观测 Agent Trace

也就是说，“检索”和“可观测性”在本项目里已经超出 PRD 的基础 MVP 要求。

### 前端已有能力

在 [brain-workbench/src/pages/ask/AskWorkspacePage.vue](/Users/yichen/Desktop/OntologyBrain/LLM-wiki/brain-workbench/src/pages/ask/AskWorkspacePage.vue) 中，Ask Workspace 已经有：

- `Quick Answer`
- `Extraction Interview`
- 单窗口 Agent 主线程
- 右侧 `Agent Trace`
- 分层 writeback 预览
- 检索证据面板
- 多轮恢复能力

所以从技术上讲，底座并不弱，真正薄弱的是产品语义层。

## 3.2 升级前的核心不足

升级前系统的主要问题不是“不能多轮追问”，而是：

### 1. 缺少显式的产品对象

系统的主对象仍是：

- `ExtractionInterviewState`
- `QuestionPlan`
- `StagedWriteback`

这些都偏向“运行态内核对象”，不适合作为前端产品对象，也不适合作为下游模块之间的稳定合同。

PRD 要求的一等公民对象并不存在：

- `InterviewSession`
- `CandidateAsset`
- `FollowupQuestion`
- `SessionSummary`

### 2. Ask Workspace 仍偏“诊断控制台”

虽然已经有交互式问答模式，但主心智还是：

- 当前答案
- slots
- next question
- trace
- writeback preview

而 PRD 要求的是：

- session metadata
- 候选资产实时展示与纠偏
- 待追问问题池
- 会话总结
- 标准化输出

### 3. 专家无法直接修正“知识产物”

升级前用户能做的是：

- 回答下一轮
- finish 会话

但不能做的是：

- 确认某个候选概念
- 标记某个规则“待澄清”
- 忽略一个候选结论
- 给资产本身附上 expert note

这意味着系统有“提炼”能力，但没有“产品级校正”能力。

# 四、本次升级的产品方案设计

本轮实现遵循一个核心原则：

**不推翻现有 extraction 内核，而是在其上方补齐 PRD 所要求的“产品对象层”。**

## 4.1 产品设计目标

本轮实现的核心目标是把交互式问答从“执行态流程”升级成“产品可消费对象流”。

即：

- 内核状态仍然保留 `ExtractionInterviewState`
- 但外部接口和前端工作台开始围绕四个正式对象组织：
  - `InterviewSession`
  - `CandidateAssetList`
  - `FollowupQuestionList`
  - `SessionSummary`

## 4.2 设计原则

### 原则 1：内核状态不丢

原有的 `ExtractionInterviewState` 仍然保留，因为它承担：

- 过程驱动
- 状态恢复
- turn trace
- writeback staging
- runtime 内部逻辑

### 原则 2：产物对象上升为主合同

新增对象不是附属字段，而是后续产品和模块之间的正式桥梁。

### 原则 3：不把 Hermes 变成领域逻辑宿主

Hermes 仍然只作为 runtime/orchestrator，不承载 extraction 的业务规则。产品逻辑、候选资产逻辑、follow-up 逻辑和状态构建仍留在 Personal Brain backend。

### 原则 4：前端从“流程解释”转向“产物呈现”

`Agent Trace` 仍保留，但降级为辅栏。主产品心智开始转到：

- 当前 session 是什么
- 正在沉淀哪些候选知识
- 还有哪些问题没问清
- 当前阶段总结了什么

# 六、核心技术实现

## 6.1 后端实现

### 6.1.1 `CandidateExtractor`

新增文件：
[ src/personal_brain/extraction/candidate_extractor.py ](/Users/yichen/Desktop/OntologyBrain/LLM-wiki/src/personal_brain/extraction/candidate_extractor.py)

这个模块负责把 extraction state 中的运行信息映射成 5 类候选资产。

当前实现策略是“规则化抽取 + 状态合并”，而不是全 LLM 自由生成。

#### 抽取逻辑

- `concept`
  - 基于 `current_object`
  - 结合 `definition / key_claims / current_answer_summary`
- `heuristic`
  - 基于当前总结句和知识目标
  - 输出 statement、适用条件、非适用条件
- `case`
  - 基于 `examples` 或最新用户输入中的案例线索
- `signal`
  - 从第一条 evidence 提取关键证据
- `boundary`
  - 根据 `scope / open_questions / missing_slots` 提取边界项

#### 合并逻辑

`_merge()` 做了一个很重要的设计：

- 如果资产还是 `draft`，允许系统自动刷新 summary/content
- 如果资产已被人工标注状态或附上 `expert_note`，则优先保留用户锁定内容

这保证系统不会覆盖专家明确做过的修正。

### 6.1.2 `ExtractionProductBuilder`

新增文件：
[ src/personal_brain/extraction/product_builder.py ](/Users/yichen/Desktop/OntologyBrain/LLM-wiki/src/personal_brain/extraction/product_builder.py)

这个模块负责构建另外三类产品对象：

- `InterviewSession`
- `FollowupQuestion[]`
- `SessionSummary`

#### `build_session`

根据：

- 启动时传入的 session seed
- 当前 extraction state
- 当前 status / turn / goal / object

生成稳定的会话元数据对象。

#### `build_followup_questions`

把原来的 `next_question_plan.candidate_questions` 升级成正式追问池：

- 第一个问题默认 `priority=high` 且 `status=selected`
- 其余问题 `priority=medium`
- 如果资产状态为 `needs_clarification`，自动派生补充澄清问题
- 历史未激活问题会转为 `answered` 等状态

这让 follow-up 从“一条下一问”升级成一个可管理的池。

#### `build_session_summary`

聚合当前资产和状态，输出：

- 关键概念
- 关键规则
- 关键案例
- 边界项
- 未解决项

成为后续模块可直接消费的 session 结果对象。

# 九、当前架构评价

## 9.1 为什么当前路线是对的

这次升级再次证明：**不需要从 0 重写。**

原因有三点。

### 第一，原有底座足够强
现有系统已经具备：

- wiki-first retrieval
- raw evidence augmentation
- extraction state machine
- state persistence
- staged writeback
- traceability
- frontend workbench shell

这些都是最贵的部分，重写只会浪费已验证资产。

### 第二，问题主要在产品语义层
之前的不足并不是“技术做不到”，而是：

- 产品对象没有站起来
- UI 没围绕产品对象组织
- 会话结果没有变成标准化产物

本轮正是沿这个方向补齐，而不是另起炉灶。

### 第三，符合 AGENTS.md 的层边界
整个升级没有破坏仓库原本的层设计：

- raw 仍是 raw
- wiki 仍是主回答层
- extraction 仍在 backend
- Hermes 仍只做 runtime/orchestrator

这点非常关键，因为它保证后续还能持续演化，而不是被短期产品需求拖成一个脆弱耦合系统。

# 十、当前不足与技术债

尽管本轮升级是有效的，但也有明确不足。

## 10.1 Product Object Layer 仍然是“映射层”，不是完整领域层
目前的 `session / candidate_assets / followup_questions / session_summary` 已经是正式对象，但还主要是从 extraction state 派生而来。

更成熟的下一步应是：

- 把这些对象逐步从“派生字段”升级成“独立领域对象”
- 支持更完整生命周期管理

## 10.2 资产抽取尚不够深
当前 `CandidateExtractor` 以规则法为主，优点是稳定，缺点是上限有限。

未来需要一个更强的混合策略：

- 规则约束
- LLM 提议
- schema 校验
- evidence grounding
- merge/merge-safe 更新

## 10.3 资产编辑目前还是最小操作
现在 UI 上支持：

- confirm
- needs_clarification
- reject

但还没有：

- 真正编辑 content_json
- 删除资产
- 合并资产
- 资产 diff 视图

这些会在共编阶段进一步展开。

## 10.4 Follow-up Pool 仍偏展示，不是完整 workflow
当前问题池能看、能显示 priority/status，但还没有：

- 单独冻结某条问题
- 标记“稍后再问”
- 追问历史管理
- 追问与资产之间更强的引用关系

# 十一、后续计划

可以把后续规划分成短中期两个层次。

## 11.1 短期计划：完成 `prd_interaction_QA` 主目标

### 优先级 1：增强 Candidate Extractor
目标：

- 提高概念/规则/边界的抽取质量
- 把“维度1：视觉核心层（决定第一眼停留）”这类期待答案，真正上升为 candidate asset 和 session summary 中的主结论

建议：

### 优先级 2：增强 Follow-up 策略
目标：

建议引入信号：

- missing slot weight
- candidate confidence
- contradiction / ambiguity
- unresolved boundary count
- answer thinness

### 优先级 3：增强专家修正体验
目标：

- 让专家不只是“点确认”，而是真正进行轻量共编

可以增加：

- summary inline edit
- expert note inline edit
- asset content_json 局部编辑
- 标记“这条应作为最终答案”

### 优先级 4：定义 downstream export contract
目标：

- 让后续模块不再直接依赖 `ExtractionInterviewState`
- 正式消费：
  - `InterviewSession`
  - `CandidateAssetList`
  - `FollowupQuestionList`
  - `SessionSummary`

## 11.2 中期计划：进入蓝图中的 Phase 1 闭环

根据 `prd_all_v1.md`，推荐顺序仍然成立：

### Phase 1
- 交互式问答 Agent
- 共编 Copilot Agent
- 最小治理流

所以当前最合理的下一步不是去做 Skill Creator，而是：

### 1. 共编 Copilot 最小版
输入：

- confirmed candidate assets

输出：

- draft brain pages
- draft decision cards

### 2. 最小治理流
为：

- candidate assets

增加：

- `draft`

### 3. 让 writeback 从“提案”进一步进入“知识生产流”
当前 staged writeback 已经是不错基础，但后续要和 candidate assets / governance 状态统一起来。

# 十二、结论

截至目前，这个项目已经完成了一次非常关键的升级：

它不再只是一个“能多轮追问、能显示 trace 的问答控制台”，而开始具备 **交互式问答台作为知识生产入口** 的基本形态。

这次升级的真正价值，不在于多写了几个字段，也不在于多加了几个组件，而在于完成了一个非常重要的系统跃迁：

**从“执行流程中心”转向“知识产物中心”。**

具体来说：

- 原来的核心是 `state / slots / next question / trace`
- 现在开始转向 `session / candidate assets / followup pool / session summary`

这一步是 Expert Brain Studio 能不能真正成立的分水岭。

因为只有当系统真正围绕“知识产物”而不是“聊天过程”组织，后面的：

- 共编
- 标注
- 冲突裁决
- Skill 编译
- Governance

才有稳定的输入对象可以接。

所以，当前实现虽然还远未完成蓝图，但方向已经走对，而且底座已经足够坚实。下一阶段最该做的，不是推翻现有架构，而是继续沿着这条产品对象化路线，把候选资产质量、追问调度、专家修正体验和 downstream handoff 再做厚一层。
